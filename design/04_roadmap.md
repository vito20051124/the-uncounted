# 04 · P0 驗收結果與完善路線圖

---

## 1. P0 驗收：核心迴圈通過，瓶頸在呈現層

使用者實際玩過一輪，逐題回答如下。

| # | 問題 | 回答 | 判讀 |
| :-- | :-- | :-- | :-- |
| 1 | 「一天不夠用」的感覺有出現嗎？ | 「時間的感覺不太明顯，但我覺得剛剛好，並且稍微不夠用」 | **✔ 通過**。時間壓力校準正確，不必調整衰減率 |
| 2 | 有沒有在兩條路線之間猶豫？ | 「**因為沒有地圖以及可視化的方式，所以其實我不太確定我自己到底在哪裡，所以只好隨便走**」 | **✘ 主賣點失效**。路網明明有 15 組 OD 對提供多條 Pareto 最優路線，但玩家看不見自己在哪，那些選擇等於不存在 |
| 3 | 看得懂自己怎麼被拖垮的嗎？ | 「不太確定，狀態欄不夠清晰」 | **✘ 支柱三未達成**。死亡是可回溯的，但玩家讀不到 |
| 4 | 錢的壓力對不對？ | 「因為不知道地理位置所以很難知道哪裡可以賺錢，整體還在熟悉就突然死亡」 | **判定被 ② 污染**——不是經濟失衡，是資訊失衡 |
| 5 | **你會想再玩一次嗎？** | **「遊戲內容是有趣的，真的有異世界生存的感覺」** | **✔✔ P0 的目的達成** |

> **結論：核心迴圈成立，不必回頭改設計。** 全部問題集中在「玩家看不到系統正在做什麼」。
> 這是最好的 P0 結果——**要修的是呈現，不是骨架。**

## 3. 已確認的缺陷

### 3.1 真 bug（必修）

| # | 缺陷 | 根因 |
| :-- | :-- | :-- |
| B1 | **`treat` 完全沒扣錢** | reducer 的 `treat` 分支只推進時間與標記已處理，從未扣除藥膏的 1 銅。草藥治療目前是免費的 |
| B2 | **商店清單過濾器失效** | `buyable` 的 `some()` 沒有引用到物品本身——只要該節點有任一販售類服務，**全部商品都會列出**。灰棚巷買得到本地舊衣、水井旁買得到灰膏 |
| B3 | 使用者回報「只有 22 銅卻買得到 30 銅的東西」 | 待複現。目前全庫無 30 銅商品，最可能是 B2 造成的清單錯亂。**修完 B2 後須重新複驗** |

## 4. P0.5 · 呈現層大改（本輪要做的）

> **不動引擎規則，只動看得見的東西 ＋ 修 bug。**
> 引擎九條紀律不變；`src/engine/` 僅在修 B1 時觸碰。

### 4.1 版面：四區塊，1440×900 不滾動

```
┌──────────────┬────────────────────────────┬──────────────┐
│              │                            │              │
│  左：狀態     │      中：劇情與選項          │  右：面板     │
│              │                            │              │
│ · 日期時辰    │  · 敘事文本                 │ [背包]       │
│ · 潮汐        │  · 事件 tell（警訊）         │ [人物]       │
│ · 五條需求    │  · 選項（一屏看完，不滾動）    │ [狀態]       │
│   0紅→100綠   │  · 路線比較（進入選路模式）    │ [設置]       │
│ · 身體狀況簡示 │                            │  點擊展開     │
│ · 錢包        │                            │              │
│              │                            │              │
├──────────────┴────────────────────────────┴──────────────┤
│  下：SVG 地圖 —— 目前位置、四周節點、路線關係、潮汐狀態        │
└───────────────────────────────────────────────────────────┘
```

- 左欄固定 220px、右欄固定 260px、中欄自適應、地圖固定 200px 高
- **中欄選項區設下限**：若選項數超過可視高度，改為兩欄並排，**永不出現滾輪**

### 4.2 狀態欄顏色律

```
value 0   → hsl(0,   65%, 45%)   紅
value 50  → hsl(45,  70%, 48%)   琥珀
value 100 → hsl(105, 45%, 42%)   綠
```
連續插值（非分段），**讓玩家看得出「正在變差」而不是「已經很差」**。

**額外警訊層**（對應裁決 D「保持致命但警訊清楚」）：
- 任一需求 < 25：該條加脈動邊框
- 任一需求 < 10：左欄頂端出現紅字警告，明寫**還剩多久會出事**
- 有未處理傷口 / 化膿：左欄常駐提示行

### 4.3 SVG 地圖規格

| 視覺元素 | 對應資料 |
| :-- | :-- |
| 節點位置 | 依 `elevation` 決定 Y（高程越高越上方）、依既有正典方位決定 X |
| 節點外圈顏色 | `security` 1–4（越危險越紅） |
| **當前位置** | 實心填滿 ＋ 光暈 ＋ 標籤加粗 |
| 連線粗細 | `minutes`（越粗越久） |
| 連線顏色 | 該時刻的 `risk`（綠→黃→紅） |
| 虛線 | `knowledge: 'learned'` 且尚未習得（**看得到有東西，但走不了**） |
| 連線消失 | `requiresTide` 不符時**整條線從圖上移除**，並在圖上標「潮汐門已關」 |
| 選路模式 | 候選路線逐條高亮，滑過時中欄同步標示 |

> **地圖由 `nodes.json` / `edges.json` 直接生成，不手繪。** 改資料，地圖跟著改。

### 4.4 右欄面板（四個分頁）

- **背包**：物品清單，**食用／飲用／使用在此執行**（不再混在劇情選項裡）。外來之物標紅並顯示「拿出來有風險」
- **人物**：本輪 3 名 NPC 的熟識度、上次見面、你告訴過他什麼
- **狀態**：詳細身體狀況（每道傷的部位、天數、是否化膿、化膿機率）、需求的精確數值與變化率
- **設置**：字級、動畫開關、重新開始

### 4.5 3 名 NPC（裁決 B）

| id | 姓名 | 位置 | 為什麼是這三個 |
| :-- | :-- | :-- | :-- |
| `npc-quays-foreman` | 碼頭監工 | `bh:quays` | 決定你有沒有工作。**熟識度會直接改變錄取率**——關係第一次有機制後果 |
| `npc-cinder-woman` | 灰棚巷自衛會女人 | `bh:cinder` | 唯一會主動接納無籍者的人。她是第 2 層需求（安全）的門 |
| `npc-grotto-elder` | 寂裔老匠人 | `bh:grotto` | 你唯一的同類（0 靈聾／閉血）。他是第 3 層需求（歸屬）的門 |

每人三軸：`熟識 / 信任 / 情感`；久不見會衰減；`knownFacts` 記錄你告訴過他什麼——**說出你從哪來是有風險的**（`canon-07` §6）。

## 7. ★ 實跑驗收（P0.5 交付前，Claude 親自玩了四輪）

> **這一節的存在理由**：`00_pillars.md` 說「審核擋得住矛盾，擋不住無聊」。
> 前面所有的檢查都是靜態的；下面五個缺陷**沒有任何一個是靠讀程式碼發現的**，
> 全部是實際玩下去才撞到的。

### 抓到並修掉的五個缺陷

| # | 缺陷 | 為什麼靜態檢查抓不到 | 修法 |
| :-- | :-- | :-- | :-- |
| **D1** | **睡覺必死**。需求在睡眠期間以清醒速率衰減，而一夜 572 分 ＞ hydration 歸零的 480 分 → 吃飽喝足躺下的人也必定醒來時脫水歸零，連兩夜即死 | 每個數字單獨看都「有推導」；只有把**一夜的長度**和**歸零的時間**擺在一起才看得出矛盾 | 睡眠代謝 0.4 倍（`SLEEP_DECAY_MUL`） |
| **D2** | **衰減率的推導是假的**。註解宣稱反推自 canon「每日 1.5–2 磅」，但 720 分鐘**把一天當成 720 分鐘算**，而一天是 1440 | ——**宣告不等於驗收**（`review-rubric.md` ⑮）。註解寫了推導，不代表數字真的推導過 | 按 1,116 等效分鐘重推：satiety 100/1600、hydration 100/1400 |
| **D3** | **經濟破口**。跑腿送信一天可連做三趟 ＝ 24 銅，使 canon 推導出來的「一天的工剛好只夠買一天的生存」失效。實測收入 22 銅/日，是設計期望 9 銅/日的 2.4 倍 | 每份工單獨看都合理；破口在**可重複次數**這個沒有人寫的欄位 | `JobDef.maxPerDay`（計嘗試不計錄取）＋跑腿薪資按其 `src` 誠實重推為 6 銅 |
| **D4** | **敘事選項無法移動玩家**。潮汐困住事件的「繞城牆根走回灰棚巷」根本沒把人移走 → 被困在城外蒸發池三天，城外沒有井，渴死 | 資料驗證只查 id 存在，查不出「這個選項在語意上承諾了一件它做不到的事」 | `Choice.gain.moveTo` |
| **D5** | **事件像瀑布**。`MIN_REFIRE_GAP` 只管同一個事件，不同事件之間毫無間隔 → 一走進石窟街，八幕連續倒下，好感 0→25，**主線第三章在第 2 日就跑完**（設計是第 8 日） | 每個事件的觸發條件都正確；問題出在**它們之間沒有條件** | `MIN_EVENT_GAP = 120` ＋ `Cond.day` 章節閘門 |

### 最重要的一個發現：關係系統原本是死的

實測第一輪：**六日局結束，「認識的人 1」**。

原因不是事件寫得不夠，是**關係只能靠一次性事件推**——事件用完，NPC 就變成佈景。
於是主線三條路的信任門檻（35–45）**一條都到不了**，等於主線寫了卻進不去。

修法刻意**不是再多寫二十個好感事件**，而是兩件事：

1. **`talk` 動作**——一天一次、收益遞減（熟識 0 → +8，熟識 90 → +0.8）、台詞在 `data/npcs.json`
2. **`JobDef.npcOnComplete`**——**關係從她已經在做的事長出來**：扛了一天貨，監工就多認得你一分

> 第二條才是關鍵。她每天本來就在替老克瓦扛貨、替穗爾跑單。
> **把好感掛在勞動上，而不是另開一條刷好感的支線**——這既符合「他不記名字，他記手」的角色設定，
> 也避開了 DoL 最大的毛病：點擊即得的重複行為。

### 修完之後的實跑結果（14 日局，走遍全城、天天說話）

```
D1 刮下殘滓 → D2 讀到普查公告 → D4 城衛查籍（轉身就走）→ D7 ★★ 接受寂庭擔保
不重複事件 32 / 46　認識的人 5　走過 6 種路段　里程碑 D6 達成
死因：第 9 日，吊車坡道的舊傷未處理引發敗血（當時身上剩 1 銅，買不起 1 銅的藥膏）
```

**主線落在設計的第 7 日閘門上**，而那個死因正好是本作的命題本身——
不是被隨機事件殺死的，是**因為窮而沒有處理一件小事**，一路可回溯。

### 新增的回歸測試（煙霧測試 12 → 15 項）

| # | 測試 | 鎖住什麼 |
| :-- | :-- | :-- |
| ⑬ | 睡滿一夜不會渴死 | D1 |
| ⑭ | 單日事件數 ≤ 8 | D5 |
| ⑮ | 12 日的說話＋做工可把信任推過 35 | 主線可達性（關係系統死掉時這條會紅） |

> ⑮ 在測試中會把傷勢清空——因為它要量的是**關係成長速率**，不是傷病存活率。
> 兩者混在一起會讓這條測試在該紅的時候綠、該綠的時候紅。

### 本輪新增的內容

| 項目 | 數量 | 備註 |
| :-- | --: | :-- |
| 事件 | 28 → **46** | 第二章殘滓、第三章三條路的開場、五條關係線、地點拉力 |
| NPC | 3 → **5** | 新增同輩：穗爾（市集書記學徒）、闕（碼頭散工）——**兩人皆友情／戀愛可達** |

| 設計文件 | +1 | **`design/05_main_story.md`** 主線《名字》 |
| 局長度 | 6 → **14 日** | 主線第三章的門檻在第 8 日後才到得了 |

> **戀愛線不開任何機制優勢**（`00_pillars.md` 反 DoL 條款二）。
> 情感達標後的事件永遠同時提供「維持朋友」與「更進一步」，且前者不減損任何數值。

### ★ 一條被超出的紀律，必須明說

`01_architecture.md` §11.1 訂了「**`src/engine/` 總行數上限 1,200 行。超過就是在蓋 P1。**」

**現在是 1,590 行，超出 33%。**

這條規則的用意是「別在 P0 階段偷蓋 P1」。而本輪依使用者指示開始做主線與關係系統——
**那本來就是 P1 的東西**。所以這不是紀律失效，是階段轉換：

> **P0 於本輪結束。此後 `game/` 進入 P1，行數上限解除，改以「存檔相容 ＋ 單元測試覆蓋」為新的約束。**

不把它寫下來的話，下一輪會有人以為 1,200 這條還在，然後在錯誤的前提下做決定。

## 8. ★★ 第五輪：死亡系統徹查（使用者回報「角色無法死亡」）

> 使用者的回報只有一句話：**「我發現角色無法死亡」**。
> 徹查之後確認 **27 項缺陷**（另有 5 項稽核發現被敵意複驗推翻），
> 而它們**收斂成兩個結構性根因**，不是二十七個獨立 bug。

### 兩個根因

> **根因一：引擎的結算時間軸是「夜」，UI 的警示時間軸是「分鐘」。**
>
> 需求死亡、傷病進程、剝奪計數**全部只在 `case 'sleep'` 發生**
> （`checkDeath` 散在 5 個 case，而 travel/work/buy/sell/useItem/treat 六個完全沒有），
> 而 `App.tsx` 用 `DECAY_PER_MIN` 外推分鐘級 ETA。
> 於是同一個紅框**既說謊又脫敏**：0% 致死率的體溫獨佔「再不處理會死」，
> 而真正會死的飢餓紅字要連喊 62.8 小時才兌現。
>
> **實測：不吃不喝但不睡覺，在城裡遊蕩 16.7 天不會死，兩個計數器恆為 0。**

> **根因二：`38.5%` 的語域被抄錯，然後被實作成每夜重擲。**
>
> `canon/07` §4.1 的但書明訂 38.5% 只適用**嚴重創傷**且**判定一次**。
> 而 `design/01_architecture.md` 舊第 269 行寫的是
> 「**她在任何地方都適用那個數字**」——那句話被實作成三段**每夜重抽**，
> 加上**傷口永不痊癒**。
>
> **實測：一道 2% 路段擦傷在 14 日窗口內致死率 95.6%；
> 300 seed 跑分死亡率 87%，其中 93% 死因是敗血，平均第 8.2 日。**
>
> 而 `body.ts` 檔頭、UI 按鈕、煙霧測試 ④ **三處同時宣稱那是 5.2%**。

### 兩個假綠燈（比缺陷本身更該記一筆）

| 測試 | 它為什麼是假的 |
| :-- | :-- |
| ③「故意餓死會觸發死亡」 | **手動注入 `stats: { hungryTicks: 3 }`**——一個對局中不可達的狀態。就算遊戲裡根本沒有東西能讓那個計數器增加（正是使用者回報的狀況），這條測試照樣全綠。**它測的是死亡訊息，不是死亡可達性。** |
| ④「未處理割傷死亡率 ≈5.2%」 | **在測試檔裡自己重寫一遍算式並驗證那個算式，完全沒有呼叫 `progressInjuries`。** 於是程式真正在跑的「每夜重擲」被這條測試完整放過。 |

> 這是 `review-rubric.md` ⑮「**宣告不等於驗收**」在遊戲側的重演，而且是我自己犯的。
> **一條測試如果靠注入不可達的狀態才會綠，它保護的是那個狀態，不是那個功能。**

### 三個最惡劣的謊（玩家付出稀缺資源，換到精確的 0）

1. **`ev-wound-notice` 的治療選項完全不進引擎**——事件寫全域 flag `treated-herbs`，
   而 `body.ts` 讀的是 `treated:<傷口id>:<方式>`。玩家付了 1 銅／燒掉一片 OK 繃，
   化膿率**一點都沒降**，而遊戲當場回饋「你成功了」。死因回溯還會列出那個決定。
2. **化膿之後治療效果精確為 0**——`①` 被 `!infected` 擋住，而 `②③` 不讀 `treatedDay`。
   UI 仍在收 1 銅、仍寫著「化膿 34% → 21%」。
3. **體溫在 UI 是致命的，在引擎裡 0% 致死**——而 canon 明載鹽澤是海洋性氣候、
   枯收季秋高氣爽，全知識庫的低溫致死數據**全部**在斷脈／大寂原的灰冬。

## 9. 第六輪：理智／慾望／整潔（P0.5 收尾）

> 使用者要求：「加入慾望與理智，宣洩慾望可以用於恢復理智。以及整潔度我不知道她的
> 實際用途是甚麼，跑了幾天我也沒找到如何讓它回復，但她歸零我也沒有死亡。」

### 整潔度：使用者的觀察完全正確，而且比他想的更糟

實測確認：**`hygiene` 全遊戲沒有任何地方會回復它**——唯一的正值出現在 `initialState`（80），
之後只減不增（時間 −6.2/日、碼頭班 −20、蒸發池 −25）。它是一條**純單向槽**。

它其實**有兩個真實效果，而兩個都沒告訴玩家**：

| 效果 | 實測 | 玩家看得到嗎 |
| :-- | :-- | :-- |
| 化膿率乘數 | 第 2 日 43.6% → 第 10 日起穩定 **59.7%** | ✗ |
| 碼頭錄取率 | 第 2 日 54.8% → 第 12 日起 **35.0%** | ✗ UI **永遠印 60%** |

> 第二條是一條**活著的 UI 謊話**，而且它躲過了第五輪新增的「UI 不得硬寫機率」檢查
> ——因為那一行含 `Math.round` 而被白名單放行。

**修法**：三階洗淨，全部用**既有的正典設施**（全庫對「澡堂｜沐浴｜浴室｜盥洗」**零命中**，
本作不得自行發明澡堂）：

| 階 | 依據 | 價 | 時 | 清潔 | 限制 |
| :-- | :-- | --: | --: | --: | :-- |
| 海水沖洗 | 鹽埠碼頭「浸水的木棧橋與防潮石砌」 | 免費 | 20 分 | +12 | 有未處置傷口時不可（滷水會吃掉傷口） |
| 井邊擦洗 | 公用分水井「供應市民日常洗滌用水」 | 1 銅 | 20 分 | +18 | 日 1 次 |
| 洗滌場借盆 | 鹽民下城「衣物洗滌場」＋「洗滌皂角味」 | 1 銅 | 40 分 | +30 | 日 1 次 |

**並把兩個效果印在它自己那一列底下**（實算，不硬寫）：
`化膿 ×1.05　·　碼頭錄取 52%　　洗一次 → ×0.85／65%`

### 順帶修掉一個既有的超模

`hygieneMul` 舊版把 canon 的 34% 當成「hygiene = 100」的基準往上加，
最壞（清潔 0 ＋ 體溫 0）是 **0.34 × 1.5 × 1.3 = 66.3%**，＝釘死值的 **1.95 倍**。
而本輪要把這個數字**印在畫面上**，於是那個超模會從隱形變成一個印出來的謊。

重新錨定：canon 的 34% 量的是**不每日沐浴的常態瑟瑞恩勞工**——它本來就是「典型」不是「潔淨」。
故 **hygiene 60 ＝ 34%**，最壞情況降為 48.9%（1.44 倍）。

### 理智 sanity

- **進 `needs`（第六個 `NeedKey`），但 `DECAY_PER_MIN.sanity = 0`。** 它不是第六個要定時餵的槽，是**每一天的收據**。
- **結算掛【日界】不掛 sleep。** `advanceTime` 一直有回傳 `crossedMidnight`，而全 repo 從來沒有人讀它——這是它第一次有用途。掛 sleep 就是 §8 根因一的原地復發（測試 ㉔ 鎖死）。
- **耗損來源白名單六項**：露宿 −4／髒（<30）−3／缺水 −3／挨餓 −3／發燒 −4／三天沒跟人說話 −3。
  **明文禁止**：街頭騷擾、性威脅、被觸碰、服裝暴露、NPC 出現——後五者是 DoL trauma 的來源清單，逐項排除而不是籠統迴避。
  （孤立那一項用的是既有的 `NpcState.lastSeenDay`——**該欄位被寫入三處、從未被讀取**，這是它第一次有用途。）
- **恢復全部與性無關**：說話 +3（免費）／單間 +4／通鋪 +2／熱食 +1／做工 +1／洗淨 +1／獨處 +5~+7／看相簿 +6／第一筆工錢 +6／取得身分 +20。
- **歸零不致死、不阻斷上工、不進 `needsHazard`、不進紅框。** 唯一後果是 `fatigueMul`（1.0→1.3）：走路更耗體力、說話更花時間。
  明文否決「理智 0 就不能上工」——那是**沒有出口的吸收態**（所有解藥都要錢，而錢的唯一來源正是被它切斷的上工）。

### 慾望 desire：它是存款，不是債務

**架構決定：`sanity` 進 `needs`，`desire` 不進。這一行型別就是「點綴」與「骨架」的分界線。**
`desire` 因此永遠拿不到衰減率、拿不到進度條、拿不到紅框，也**永遠寫不進任何 `requires`**。

| 特徵 | 本作的 desire | 機械保證 |
| :-- | :-- | :-- |
| 隨時鐘累積成槽 | **否**（0/1/2 三階） | 型別上寫不進去 |
| 溢出有懲罰 | **否**（滿階零後果） | 測試 ㉘：慾望 0 與 2 的一切可觀測量完全相同 |
| 不宣洩即劣化 | **否**（對理智扣減 = 0） | 同上 |

> 使用者原話只要求一條加號（「宣洩慾望**可以用於恢復**理智」）。
> 減號是設計者自己會想加的東西，而那個減號正是 DoL 的核心迴圈。
> 刪掉它，「理智低 → 只能靠宣洩」**在數學上不成立**。

**「宣洩」實作為動作「獨處」，本輪零性內容**：0 銅、20 分、需要一個此刻沒有人的地方
（老鹽街後巷 20:00–06:00／寂裔石窟街全日），慾望歸零並回 +3+2×階段 的理智。
判準（性內容整段移除後仍可玩）**不是靠承諾通過，是靠本來就沒有東西可移除通過**。

### ★ 憲法衝突，已公開提案、待你核可

`00_pillars.md` 支柱二條款 2 **逐字**寫著「不設慾望槽」。**我沒有偷改那一句**——
原文一字未動，改為在其後追加語域限定並新增條款 5（新增計量的四道門檻），

## 10. P1 進行中

### P1-1 存檔／讀檔 ✓

> **存檔就只是狀態本身。** `GameState` 是純 JSON（所有 Map 都在 `Index`，不在 state），
> 而 RNG 無狀態（`rand(seed, stream, ...salt)`，不維護游標）。
> 這不是運氣，是紀律 1 與紀律 6 的回報——若當初 RNG 帶游標，這裡就得序列化亂數狀態，
> 而任何內容改動都會讓舊檔重播漂移。存檔測試 ② 就是這一點的驗收。

| 檔案 | 職責 |
| :-- | :-- |
| `src/engine/save.ts` | 純函數：序列化／逐級遷移／驗證。**不碰 localStorage**（紀律 1） |
| `src/ui/storage.ts` | 唯一碰 localStorage 的檔。3 手動槽 ＋ 1 自動槽 |

三個刻意的決定：

1. **自動存檔只在跨日發生，而且【死了不存】。** 否則唯一的自動檔會停在死掉那一刻，
   `00_pillars.md` 的「死亡是永久的，但保留存檔制可回檔」就成了空話。
2. **v1→v2 遷移現在就寫**，即使世上沒有一份 v1 存檔。
   存檔相容是 DoL 的慢性病，而它之所以變成慢性病，就是因為遷移機制總是在
   「已經有玩家存檔壞掉」之後才被寫。**第一次真的需要遷移時，不該是那段程式第一次執行。**
3. **驗證失敗一律拒絕載入並說原因**，不默默補成「看起來能玩」。
   本專案已因「靜默丟棄」踩過三個 blocker——一份被默默修補的存檔，
   玩家會在幾小時後才發現不對，而那時已經沒有可回去的地方。

`scripts/save-test.ts` 八項：往返保真、**讀檔後續玩與未存檔逐位元相同**、v1 遷移、
遷移後可續玩、八種壞檔全擋、驗證器不誤殺、死亡狀態可存讀、體積在配額內（第 24 日 99 KB）。

瀏覽器實測抓到並修掉：**自動存檔寫進去了但槽位列表仍顯示「（空）」**——
`slots` 只在掛載時算過一次。玩家會以為沒存成功，然後覆蓋掉它。

### P1-5 單元／性質測試 ✓

三份測試各問不同的問題：

| | 問的是 |
| :-- | :-- |
| `smoke.ts` | 玩得下去嗎（整局，一條政策） |
| `save-test.ts` | 明天改了內容，玩家的檔還讀得起來嗎 |
| **`unit-test.ts`** | **不管玩家做什麼順序，這些事都不准發生** |

> **為什麼是不變量模糊測試而不是逐個 action 斷言**
>
> 六輪下來反覆踩的是同一個 bug**類別**，不是同一個 bug：
> 事件治療寫全域 flag 而引擎讀 `treated:<id>:<方式>`／`cost.sanity` 被硬寫的五鍵陣列吃掉／
> UI 印 `hireChance` 基礎值而實算被 hygiene 拉到 35%／`sleep` 先推進時間才寫 `lastShelter`。
>
> 共同點是：**每一條路徑單獨看都對，錯在它們之間。**
> 逐個 action 斷言抓不到——它只會證明每條路徑符合它自己的預期。

七項：不變量模糊測試（400 局／13,037 步／每步驗 14 條）、**`reduce` 純度**（深度凍結輸入）、
共用報價的單調性、決定性、無效動作零副作用、每日上限、只有飢渴會致死。

**它抓到一個真的引擎缺口**：`case 'work'` **不檢查 `job.when`**——
時段限制原本只存在於 `App.tsx`，碼頭挑人窗口是 05:00–08:00，
而 reducer 會接受凌晨三點上工，只有介面在擋。又是「兩條路徑分歧」。
現在 reducer 守住自己的前置條件，跑分腳本／存讀檔／未來的介面改動都繞不過去。

> 過程中我自己寫壞了三次測試：seed 取名 `no-desire` 污染了字串掃描、
> 缺「沒推進時間就強制 wait」的防護導致空轉、數呼叫次數而不是生效次數。
> 三次都是測試的錯而非引擎的錯——但第三次順手挖出了上面那個 `when` 缺口。
> **一條會誤報的測試仍然可能有價值，前提是你去查它為什麼誤報。**

| | 貨幣 | 在第 30 日 |
| :-- | :-- | :-- |

引擎**只判定玩家自己宣告的那一條**，不做優先序瀑布——任何 if/else 的最後那個 else
一定會被讀成「其他都沒達成」，而它偏偏就是平凡。單元測試 ⑨ 是這條的機械保證。

### ★ 條件是量出來的，不是調出來的（方法比數字重要）

第一版平凡寫「三個人認得她的臉」，達成率 **91%**。逐人跑分揭穿了原因：

| | 老克瓦 | 穗爾 | 闕 | 灰姐 | 石啞 |
| :-- | --: | --: | --: | --: | --: |
| 純領工資者認得的比例 | 100% | 100% | 100% | **0%** | **0%** |
| 該節點有工作嗎 | ✔ | ✔ | ✔ | **✘** | **✘** |

「三個人」恰好就是**純領工資者的自動集合**。改成四之後：領工資組 0%、會走動組 72%。
而走動的代價量出來是 **19 銅與一個上工日，不是命**（死亡率 13.5% vs 14.5%）。

它同時抓出量尺自己的錯：第一版「會走動」政策每步從四區隨機挑一個 →
死亡率 65%、收入從 295 崩到 68，因為它整天在爬 +12m 崖梯。**那量到的是隨機遊走的代價。**
