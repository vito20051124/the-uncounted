# 01 · 系統架構總覽（Architecture）

> 上位：`design/00_pillars.md`（遊戲憲法）· `canon/00–07`（世界憲法）
> **本檔回答的是「東西怎麼組起來」，不是「內容寫什麼」。**

---

## 0. 一條總原則：引擎是純函數，內容是資料

```
reduce(state, action) -> state'
```

DoL 最大的維護債是**敘事文本與邏輯纏在同一個 passage 裡**，導致：寫手必須會寫程式、任何改動都可能造成回歸、且**幾乎無法自動測試**。

本作把這條線切死：

- **引擎（`src/`）不含任何世界內容。** 它只認識規則，不認識鹵港。
- **內容（`data/`）不含任何邏輯。** 它是宣告式的資料，由引擎解譯。
- **世界事實（`world/**` + `registries/`）不被複製。** 建置期抽取、執行期引用 id。

> **判準**：把 `data/` 整個換掉，引擎應該還能跑另一款遊戲。做不到就是切線切歪了。

## 1. 分層與資料流

```
┌─────────────────────────────────────────────────────────────┐
│ SSOT（唯讀，不由遊戲回寫）                                    │
│   world/**.md（324 條目）  registries/*.md（gazetteer 394… ） │
└───────────────────────────┬─────────────────────────────────┘
                            │ 建置期抽取（重用 codex/server/loader 解析邏輯）
                            v
┌─────────────────────────────────────────────────────────────┐
│ data/world/*.json  ← 機器產出，禁止手改                       │
│   路網節點 · NPC 名冊與關係 · 物價基準 · 階制表 · 藥草與傷病    │
└───────────────────────────┬─────────────────────────────────┘
                            │
      data/*.yaml  ← 人（與 agent）手寫的遊戲內容
      events/ jobs/ items/ routes/ schedules/ dialogue/
                            │
                            v  建置期：schema 驗證 ＋ 參照完整性檢查
┌─────────────────────────────────────────────────────────────┐
│ content bundle（具型別、已驗證、不可變）                       │
└───────────────────────────┬─────────────────────────────────┘
                            v
┌─────────────────────────────────────────────────────────────┐
│ Engine（TypeScript，純 reducer，無 I/O、無隨機來源以外的副作用）│
│   clock · needs · body · map · event · economy · relations   │
└───────────────────────────┬─────────────────────────────────┘
                            v
┌─────────────────────────────────────────────────────────────┐
│ View（渲染 state ＋ 呈現 choices，不含規則）                   │
└─────────────────────────────────────────────────────────────┘
```

**參照完整性檢查（建置期擋下，不留到執行期）**：
每個事件的 `where` 必須是真實節點 id；每個 `item` 必須存在；每個 NPC id 必須在 `dramatis_personae` 中；每個引用的地名必須在 `gazetteer` 中。**這是 `link-lint` 的遊戲版**，且同樣要求歸零。

## 2. 狀態模型（分命名空間，不是全域湯）

```ts
type GameState = {
  meta:  { schemaVersion, seed, createdAt, playtimeMinutes }
  clock: { day, minute, season, weather, tidePhase }

  pc: {
    identity: { name, appearance, pronouns }        // 開場自訂
    needs:    { satiety, hydration, stamina, warmth, hygiene }   // 0..100
    body:     { injuries: Injury[], illnesses: Illness[] }
    mind:     { stress, morale }
    skills:   Record<SkillId, { xp, rank }>
    standing: {
      registration: RegistrationState        // ★ 第 2 層需求的核心
      ranks:      Record<LadderId, RankId>   // 武技/認證/學銜/行會
      reputation: Record<FactionId|DistrictId, number>
    }
  }

  purse: { copper: number }        // ★ 一律以「銅」為基本單位
  carry: { items: ItemStack[], encumbrance }
  home:  { tier, nodeId, rentDue, security, storage: ItemStack[] } | null

  world: {
    npcs:        Record<NpcId, NpcState>
    knownRoutes: EdgeId[]          // ★ 知識模型
    knownFacts:  FactId[]
    prices:      Record<ItemId, number>
    flags:       Record<string, unknown>
  }

  ledger: DecisionRecord[]         // ★ 死亡回溯用，見 §7
}
```

### 三條狀態鐵律

1. **金錢一律以銅為整數儲存。** 1 金帝 ＝ 240 銅，非十進（`canon` 硬不變量）。顯示時才換算，**絕不以浮點金帝儲存**。
2. **傷病是物件不是數字。** `Injury { type, severity, site, infected, treatedAt, source }`。因為主角**永遠不能被 `光耀+淨` 治癒**（`canon-07` §4.1），傷必須能被個別追蹤、個別惡化、個別處理。
3. **需求為惰性計算。** 不跑逐分鐘 tick；`advanceTime(minutes)` 一次結算該區間的衰減。決定性、便宜、可測試、存讀檔無漂移。

## 3. 時間模型

> **★ 時間分兩層（`when.hours` 的語意在此釘死）**
> **正典的鐘點制目前自相矛盾**：`calendar-and-festivals.md` 記 二鐘＝07:00、十鐘＝18:00；`occupations.md` 日班記 二鐘＝07:30、四鐘＝10:30、九鐘＝15:00；同檔夜班又記 二鐘＝**03:00**。**二鐘同時是三個時刻，且鐘距不等**（四→五鐘 30 分，九→十鐘 180 分）。
>
> **處置**：
> 1. **引擎只認 `minute: 0..1439` 的整數。** 所有 `when.hours` 一律為 **24 時制的小時**，不是鐘。
> 2. **鐘點映射是資料**，存 `data/world/bells.json`，UI 顯示時才換算。**不在遊戲側偷選一個版本**——鐘點制的統一是世界側的債，走 world-forge 修正。
> 3. **附帶機制**：手機的「精確時鐘」價值正是建立在這個資訊不對稱上——**她看得到 07:23，本地人只聽得到鐘聲。**

- **基本單位：分鐘（整數，比照金錢）。** 一日 1440 分。**禁止小數分鐘、禁止「一時段＝一回合」**——一旦失去解析度，路網的「18 分 vs 41 分」這個主賣點直接死掉。
- 每個行動消耗分鐘；**時間是本作最稀缺的資源**（比錢還稀缺，因為錢由時間換來）。
- **日相**（晨／晝／昏／夜／深夜）驅動路網、NPC 排程、事件池、危險度。
- **結算點**：
  - `advanceTime()` → 需求衰減、體溫、遭遇檢定
  - **睡眠** → 傷病進程、疾病判定、恢復、關係衰減、房租計數
  - **季節轉換** → 物價、天候、體溫壓力（**冬天會殺人**）
- **潮汐**：鹵港為潮間帶城市（其空間邏輯即「潮間帶三方角力」）。潮相改變路網，**這是既有正典而非新增設定**。

## 4. 地圖與移動（★ 本作對 DoL 的主要改進）

### 4.1 資料結構

> **★ node id 必須加城市前綴（原文「直接沿用 gazetteer id」是錯的）**
> `registries/gazetteer.md` 存在**真實撞號**：`district-cathedral-rise` 同時是春冕都「聖座大聖堂教區」（人口 5,200）與鹵港「聖鹵大聖堂區」（人口 2,000）。
> 另有 `landmark-futures-exchange-hq`、`landmark-merchants-senate-hall`、`landmark-valerius-conduit-hub` 等重複列——多數是同一實體的刻意重登，但**用 Map 建索引會靜默覆蓋**。
> **故遊戲一律用 `<城市>:<id>` 形式**（如 `bh:district-cathedral-rise`）。

```ts
type Node = {
  id: NodeId                  // ★ 城市前綴 + gazetteer / district id
  districtId, indoor, elevation
  services: ServiceId[]       // 賣什麼、能睡嗎、能洗嗎、能治傷嗎
  openHours?: HourRange[]
}

type Edge = {
  id, from, to
  baseMinutes, elevationDelta
  when?:      { hours?, tide?, season?, weather? }   // 不滿足＝此邊不存在
  requires?:  { pass?, key?, skillRank?, registration? }
  risk:       { base: number, byHour?: Record<Hour, number> }
  knowledge:  'public' | 'learned'
  tell?:      string          // ★ 風險的敘事前兆，見 §5.3
}
```

### 4.2 四個機制（逐條對應 DoL 的四個毛病）

**① 邊是真的路，不是瞬移。**
移動消耗時間與體力；高程差加乘體力消耗（藤丘城按等高線分階級、綠谷古堡「高程即防務層級」——**爬坡在這兩座城是字面意義的階級移動**）。

**② 路線選擇是真決策。**
引擎**不自動走最短路**。玩家指定目的地，引擎列出 2–4 條**性質不同**的路線：

| 路線 | 時間 | 風險 | 體力 | 備註 |
| :-- | --: | :-- | --: | :-- |
| 穿灰棚巷 | 18 分 | **高（夜）** | 低 | 省時間，但天黑後那條巷子不是同一條巷子 |
| 沿碼頭繞 | 41 分 | 低 | 中 | 安全，但趕不上宵禁 |
| 走上坡舊道 | 33 分 | 低 | **高** | 帶著貨會走不動 |

**③ 同一段路在不同時間是不同的邊。**
白天的邊與夜裡的邊是兩筆資料。宵禁（《夜閉令》）、漲潮、封街、暴雨——**改變的是圖本身，不是圖上的一個修正值**。

**④ 知識模型：捷徑本來就存在，你只是不知道。**
`knowledge: 'learned'` 的邊不在玩家的圖上，直到她：
- 從 NPC 口中得知（**關係系統與地圖系統在此交會**）
- 花時間在該區閒晃／觀察
- **買一張實體地圖**（一件真實的、要花錢的、會被偷的物品）
- 跟著別人走一次

> **買地圖是真實的遊戲進程。** 這一條同時解決了「地圖沒有成長感」與「探索沒有回報」兩個問題。

### 4.3 渲染

節點座標由既有 `_citymap.md`（ASCII 方位圖＋高程）推導，**以 SVG 圖層疊在 AI 生成的城市底圖上**。同一份資料同時餵 Codex 的地圖視圖與遊戲——**地圖不是畫出來的，是算出來的**。

## 5. 事件系統

### 5.1 選取管線

```
候選 = events.filter(where 匹配 ∧ when 匹配 ∧ requires 通過 ∧ once 未觸發)
挑選 = 加權隨機（seeded）或劇本指定
呈現 = text + choices
解析 = choice.effects（決定性） + choice.risks（機率，但須已被 tell 預告）
```

### 5.2 內容格式（宣告式，寫手不碰程式）

```yaml
id: ev-brine-quay-daylabour
where: [district-harbor-quays]
when:  { hours: [5, 11], weatherNot: [storm] }
requires: { stamina: ">30", injurySeverity: "<2" }
weight: 12
tell: 監工在人群裡挑人，先挑手上有繭的。
text: |
  ...
choices:
  - label: 扛一天鹽袋
    cost:  { minutes: 480, stamina: -35, hygiene: -20 }
    gain:  { copper: 11 }
    risks:
      - { chance: 0.08, tell: 第三趟之後腰就開始發燙, effect: { injury: back-strain } }
  - label: 算了
    cost: { minutes: 10 }
```

### 5.3 ★ `tell` 欄位是強制的（由支柱三導出的架構要求）

> **鐵律：不得存在無預警、不可規避、且致命的隨機事件。**

因此**任何帶致命風險的事件與路段，schema 層強制要求 `tell`**——一句寫在敘事裡的前兆。建置期驗證：`risk.severity >= lethal` 而無 `tell` 者，**建置失敗**。

> 這把「公平性」從設計者的自律變成**編譯器擋得下來的東西**。

## 6. 經濟

- **一切以銅計。** 錨點（既有正典）：**1 銅 ≒ 兩磅黑麥麵包**；粗工日薪 **8–15 銅**；1 金帝 ＝ 240 銅。
- **物價來自世界**：既有條目已載的價格直接引用，遊戲只補真正缺的。
- **工作表（`data/jobs/`）**：

| 欄位 | 說明 |
| :-- | :-- |
| `where` / `when` | 地點與時段 |
| `requires` | 技能階／體況／**登記狀態**（★ 無籍者拿不到好工作，這就是第 2 層需求的壓力來源） |
| `minutes` / `pay` | 時間與收入 |
| `risks` | 與事件同一套風險系統 |
| `repEffects` | 對特定行會／城區的聲望影響 |

> **出賣身體是這張表上的一列**，欄位與扛鹽袋、抄寫、採藥完全相同。它的特別之處只在後果的種類，不在篇幅（`00_pillars` 支柱二）。

- **魔法是純消耗品**：她能買血晶器物、能使用，但**永遠無法充能**（`canon-07` §4.1）。這是一條只出不進的錢坑，也是本作最貴的東西。

## 7. 傷病、死亡與回溯

### 7.1 傷病是流程不是數字

```
未處理傷口 → 感染判定 → 發熱 → 失能（無法工作）→ 敗血 → 死
      ↑ 清創(需淨布+清水)   ↑ 藥師(要錢)      ↑ 休養(要時間=要錢)
```

主角**永遠不能被 `光耀+淨` 治癒**（`canon-07` §4.1）。

> ### ★ 更正（第五輪徹查）：38.5% 的語域
>
> **本節原本寫的是**：「無魔法可用者的嚴重創傷感染死亡率為 38.5%，**她在任何地方都適用那個數字**。」
>
> **那句話是錯的，而且它直接造成了一個把遊戲玩壞的 blocker。**
>
> `canon/07` §4.1 的但書明訂 38.5% 只適用於**嚴重創傷**（severity 3）且無 `光耀+淨` 可用者，
> 而**一般傷口的錨點是 34%（未處置）／21%（凡俗處置後）**（`world/catalogs/hollow-flora.md`）。
>
> 「在任何地方都適用」被實作成了「**每一夜都重擲 38.5%**」，加上傷口永不痊癒，
> 結果是**一道 2% 的路段擦傷在 14 日窗口內的累積死亡率 95.6%**——
> 300 seed 跑分實測死亡率 87%，其中 93% 死因是敗血。
> 而 `body.ts` 的檔頭、UI 的按鈕、煙霧測試 ④ 三處同時宣稱那是 5.2%。
>
> **正確的規格**（已實作於 `src/engine/body.ts`）：
>
> | 階段 | 機率 | 語域 | 出處 |
> | :-- | --: | :-- | :-- |
> | 未處置 → 化膿 | 34% | 一般傷口 | `canon: hollow-flora.md` |
> | 草藥處置 → 化膿 | 21% | 一般傷口 | `canon: 同上` |
> | 無菌敷料 → 化膿 | 8% | 一般傷口 | `derived: 此世無無菌敷料，外插` |
> | 化膿 → 嚴重（未處置） | 40% | — | `invented: 待校正` |
> | 化膿 → 嚴重（已處置） | 15% | — | `derived: canon 具名案例多存活，dret 同班守衛仍死於第 21 日` |
> | 嚴重 → 死亡（未處置） | **38.5%** | **僅嚴重創傷** | `canon: canon-07 §4.1` |
> | 嚴重 → 死亡（已處置） | 19% | 僅嚴重創傷 | `derived: 38.5% 折半` |
>
> **且每一階段只判定一次**，各有 **2 日**處置窗口（錨點是 `00_pillars.md` 自己的範例鏈
> 「第 3 日割傷 → 第 9 日死於敗血」＝ 6 日走完三階）。**傷口會痊癒。**
> 未處置擦傷的最終死亡率 ≈ 0.34 × 0.40 × 0.385 ≈ **5.2%**，一片 OK 繃降到約 1.2%。
>
> **教訓**：這一節寫錯的不是數字，是**語域**。一個帶但書的 canon 數字被抄成無條件，
> 而下游沒有任何一道檢查會發現「這個機率被套用在錯誤的階段上」。
> 這與 `review-rubric.md` ⑮「宣告不等於驗收」是同一類錯誤——
> **註解寫了推導，不代表數字真的推導過**。

**感染的主要後果不是死亡，是失能**：發燒者無法上工 → 沒收入 → 沒錢吃飯。
這才是 `00_pillars.md` 範例鏈的字面意思——**不是骰子殺了你，是貧窮殺了你**。

### 7.2 死亡回溯（Post-mortem）是架構要求

`state.ledger` 逐筆記錄決策：時間、地點、選項、當時可選而未選的替代方案、當時的金錢與需求值。

死亡時渲染成一條**玩家看得懂的因果鏈**，並標出每一步當時存在的出口與它們的價格。

> **死亡是教學，不是懲罰。** 這是支柱三在架構上的具體落實——它要求狀態必須攜帶歷史，所以 `ledger` 不是除錯工具，是遊戲功能。

## 8. 關係系統（服務第 3 層需求）

```ts
type NpcState = {
  acquaintance, trust, affection      // 三軸，非單一好感度
  lastSeenDay                          // 久不見會衰減 → 讓第 3 層成為「穩定狀態」
  knownFacts: FactId[]                 // 她知道你什麼（★ 說出真相是有風險的）
  obligations: Obligation[]            // 人情債，雙向
  schedule: ScheduleEntry[]            // 由其正典條目導出：何時在哪
}
```

- **NPC 不站在原地等。** 排程由 `dramatis_personae`（88 人）與其角色檔導出。錯過就是錯過。
- **戀愛是關係系統的一條軌**，門檻為 trust＋affection＋時間，**不是獨立系統**（支柱二）。
- **`knownFacts` 是本作的秘密系統**：她可以選擇告訴誰她從哪來。依 `canon-07` §6，**說出真相沒有好處**——最好被當瘋子，最壞被當遺物竊賊。但對某個對的人說，是關係深化的關鍵節點。

## 9. 存檔與相容

- **有版本號的 schema ＋ migration 函式鏈**（`v1→v2→v3`）。存檔相容是 DoL 的慢性病，從第一天就處理。
- **seeded RNG 存進存檔**：可重播、可除錯、可做回歸測試。
- 存檔為 JSON ＋ 壓縮。

## 10. 測試策略（DoL 做不到、而我們必須做到的事）

| 層級 | 方法 |
| :-- | :-- |
| **引擎** | 純 reducer → 單元測試。給定 state ＋ action，斷言 state' |
| **內容** | 建置期 schema 驗證 ＋ 參照完整性（`link-lint` 的遊戲版，同樣要求歸零） |
| **公平性** | 建置期擋下「致命但無 `tell`」的事件與路段 |
| **平衡** | ★ **模擬跑分**：以腳本代理跑 1,000 場，統計死因分布、死亡日中位數、金錢曲線、各層需求達成時數。**人力試玩永遠找不出來的平衡問題，模擬找得出來** |
| **可玩性** | **只能人玩。** 審核擋得住矛盾，擋不住無聊——新事件必須實際跑過一次 |

## 11. 建置順序（★ 先驗證好玩，再蓋架構）

> **反直覺但關鍵**：不要先蓋這份架構。先做一個小到近乎粗糙的東西，確認核心迴圈好玩。

| 階段 | 內容 | 驗收 |
| :-- | :-- | :-- |
| **P0 · 迴圈驗證** | **6 節點／14 邊／3 工作／16–20 事件／6 物品／5–7 個遊戲日** | **「餓 → 找錢 → 冒險 → 睡」這個循環好玩嗎？** 不好玩就回來改設計，不要往下蓋 |
| **P1 · 引擎骨架** | 本檔 §2–§7 的具型別實作、存檔、建置期驗證 | 單元測試綠燈；內容參照完整性歸零 |
| **P2 · 鹵港垂直切片** | 3–4 城區、5–8 名既有 NPC、20–30 遊戲日、主線＋2 支線 | 模擬跑分平衡合理；人玩得下去 |
| **P3 · 內容擴張** | 沿用 world-forge 的 BRIEF→生成→敵意審核→整合流水線量產事件 | 每輪審核九項＋機械驗算五查＋實跑 |
| **P4 · 美術與打磨** | 場景圖／立繪／物品圖示、UI、音效 | 體積預算內、全離線無 CDN |

### 11.1 ★ P0 就必須守住的九條紀律（違反者 P1 需重寫）

原本只列三條，經獨立壓力測試後擴為九條。**前六條是「不現在做就一定要重寫」等級。**

| # | 紀律 | 為什麼現在就要 |
| :-- | :-- | :-- |
| 1 | **引擎零 UI 耦合** —— `src/engine/**` 不 import 任何 Preact | 換框架時只動 View 層 |
| 2 | **內容零邏輯** —— `data/**` 是純資料，判斷式走宣告式條件 | DoL 最大的維護債就在這裡 |
| 3 | **金錢一律以銅為整數** —— 1 金帝 ＝ 240 銅，非十進 | 浮點金帝會在跨輪對帳時累積誤差 |
| 4 | **時間分兩層**：引擎只認整數分鐘；鐘點映射存 `data/world/bells.json` | 正典鐘點制自相矛盾，見 §3 |
| 5 | **reducer 純函數，且 `ledger` 從第一行就寫** | 不做死亡回溯畫面可以，**不記帳不行**。P0 若不吐結構化變更記錄，P1 要把每個 reducer 重寫一遍 |
| 6 | **seeded RNG 分流且無狀態**：`rng(stream, ...salt)` 由 `hash(seed, stream, day, nodeId, eventId, attempt)` 導出，**不維護游標** | 單一全域序列下，新增一個事件就位移整條後續序列，**回歸測試全爆、存檔重播失效**。約 30 行 |
| 7 | **所有條件走同一個求值器** `evaluate(cond, ctx)` | 禁止任何地方寫 inline `if (state.pc.needs.satiety < 20)`。條件語言可以小，**入口只能有一個** |
| 8 | **時間整數化**（同 §3） | 失去解析度＝主賣點死掉 |
| 9 | **node id 加城市前綴**（同 §4.1） | gazetteer 有真實撞號 |

> **另加一條防膨脹硬規則**：**`src/engine/` 上限 1,200 行。超過就是在蓋 P1。**
>
> **判準為「實際程式行數」（排除註解與空行）**——本規則的用意是防止過度建造，而註解不是過度建造。
> P0 實測：8 模組、總 1,239 行、**實際程式 960 行**（body 70／clock 65／cond 88／events 34／map 128／reduce 339／rng 43／types 193）。

### 11.2 ★ P0 的驗收不是「能跑」，是「拿得到答案」

> **P0 的產出不是一個遊戲，是一份答案。**

因此 **局末摘要（第 5/7 日結束）比死亡回溯畫面更該先做**：總收入／總支出、餓了幾次、走過哪些路線、**哪條走最多次**、遇到幾個不重複事件、**白跑幾趟**。

**沒有這個畫面，使用者玩完只會說「還好」，拿不到可行動的訊號。**

### 12.1 A4 對架構的具體衝擊（★ 值得單獨記一筆）

「隨機投放、落點不可推導」不只是設定，它**移除了一整類設計**：

- **沒有「回到抵達點就能回去」的機制** —— 她抵達的地方從來就不是任何一個「點」
- **殘滓沉積是物證但不是線索** —— 它證明事件發生過，卻完全不指向裝置在哪
- **主線不可能是「找到遺物 → 解決問題」** —— 找到了也沒有人看得懂（`canon-07` §2）

> 故本作的主線**不是尋物，是安身**。這與 `00_pillars` 的馬斯洛脊椎完全同向：**遊戲的目標從第一天起就是第 2 層需求，不是第 5 層的真相。**

## 13. 技術選型（A6 定案）

### 13.1 選型

| 層 | 選擇 | 理由 |
| :-- | :-- | :-- |
| 語言 | **TypeScript**（全棧） | 引擎需要具型別狀態與 schema；存檔 migration 靠型別把關 |
| 建置 | **Vite** | 產出純靜態、可全離線；建置期跑 schema 驗證與參照完整性檢查 |
| UI | **Preact**（約 4 KB gzip） | 文字遊戲的 UI 不複雜（文本面板／選項列／狀態列／SVG 地圖／背包）。React 太重，Preact 夠用且體積可控 |
| 內容格式 | **YAML → 建置期編譯為 JSON** | 寫手友善；**執行期不帶 YAML parser** |
| 存檔 | JSON ＋ 壓縮，帶 schemaVersion 與 migration 鏈 | 存檔相容是 DoL 的慢性病，從第一天處理 |
| 隨機 | **seeded PRNG，seed 存進存檔** | 可重播、可除錯、可做回歸測試 |

> **★ 選型是低風險的，因為引擎與 UI 零耦合。** 引擎是純 reducer，不 import 任何 UI 套件。哪天要換 Svelte 或包成桌面程式，動的只有 View 層。

### 13.2 全離線的三個實際問題

**① 中日韓字型 —— ★ 原規劃有誤，已推翻**

原本規劃「建置期字型子集化」。**調查 `codex/` 後推翻：不需要做。**

codex 的 `public/` 下**零字型檔**（掃 `*.woff*` / `*.ttf` / `*.otf` 皆無命中），全站靠**系統字型堆疊**：

```css
--font-serif: "Cinzel", "Noto Serif TC", "Songti TC", "PMingLiU", serif;
--font-sans:  system-ui, -apple-system, "Segoe UI", "Noto Sans TC", sans-serif;
--font-mono:  "Fira Code", "Cascadia Code", "Consolas", monospace;
```

每個堆疊都在西文字型後接一個繁中字型——**西文取魔典感，中文自動 fallback 到系統宋體／黑體**。全站無任何 `@font-face`，**零下載、零位元組**。

> **決定：v1 沿用此策略。不做字型子集化，省下一整條建置管線。**
> 僅當視覺一致性真的需要指定字型時才重啟評估——屆時再處理 5–15 MB 原始檔的問題。

**② 圖片體積是專案大頭**

場景圖 50–150 張 ＋ NPC 立繪 ＋ 物品圖示。須訂體積預算並強制執行（建議：全部資產 ≤ 150 MB，單張場景圖 ≤ 400 KB，採 WebP/AVIF）。**建置期超標即失敗**，比照 `tell` 欄位的作法。

**③ 交付形態**

- **開發期**：Vite dev server
- **交付**：純靜態 bundle ＋ 一支比照 `codex/scripts/serve.ps1` 的極簡啟動腳本（純 ASCII、`$PSScriptRoot` 反推路徑）
- **v2 選項**：包成桌面程式（Tauri）。**現在不做**，但引擎的零耦合保證了之後做得到

### 13.3 承襲既有紀律

- 重型前端函式庫由 Claude 親自 vendored（agy 無法可靠手寫 min.js，曾產出壞的 6 KB stub）
- Node 讀寫 markdown／YAML 一律指定 **UTF-8**（繁中 UTF-8-無-BOM），且路徑正規化 `.replace(/\\/g,'/')`
- **Node ≥ 20、ESM（`"type": "module"`）**——與 `codex/` 一致
- **鎖 `chokidar@^3.6.0`**：v4 已移除 glob 支援，`codex/server/app.js` 現行的 watchPaths 寫法在 v4 下會失效
- **遊戲用埠 `4174`**（`codex/` 佔用 4173；已確認 4174 未被占用）
- 啟動前先 `Get-Process node | Stop-Process` 避免佔埠連到過期版本（EADDRINUSE 會讓你連到過期版本）

### 13.4 可直接重用的 `codex/` 資產

| 資產 | 用法 |
| :-- | :-- |
| **`codex/server/parse-registries.js`** 的 `parseGazetteer` / `parseDramatis` / `parseGenericTable` | **全部具名 export、純函式、零依賴**。一行 import 就把 `gazetteer.md`(85 KB) 與 `dramatis_personae.md`(38 KB) 變成結構化陣列。**最低耦合、最高收益** |
